# RocketVault Dashboard — JWKS Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> for the multi-task breakdown below, or superpowers:executing-plans if executing
> this plan directly, top to bottom.

**Goal:** A single admin screen for the **JWT signing key** — view the published
JWK set from the public `/jwks.json`, and rotate it (admin) where the configured
key source supports rotation. Mounted at `/app/admin/jwks`.

**⚠ Scope boundary, read first.** This epic is about the key RocketVault signs
its own session JWTs with (`internal/signing`, RS256/ES256). It has **nothing to
do with Epic 03's vault key management** (`/api/v1/vaults/{vault}/keys`, user
cryptographic material). They share the word "key" and nothing else: different
routes, different auth model, different service, different storage. Do not reuse
`src/api/keys.ts`, `src/components/keys/*`, or the key detail route here, and do
not surface this screen anywhere in vault-mode nav. The one real overlap is
incidental and worth knowing: with `jwt.key_source: self_pki` the signing key is
itself stored as a `model.Key` row named `_jwt_signing` with `UserID: uuid.Nil`
(`internal/signing/self_pki.go:24, 130, 211`) — an implementation detail, not a
reason to merge the two UIs.

**Architecture:** See `docs/superpowers/specs/2026-09-08-webapp-dashboard-epics-design.md`
§§ 2, 6 (Epic 12). Mixed auth: the read is public, the rotate is admin. Builds on
Phase 0's `src/api/client.ts` and the `admin.tsx` layout route
(`requireGlobalAdmin`, foundation Task 10, Step 2).

**Tech Stack:** unchanged from foundation.

**Conventions to follow:** see foundation plan §Conventions — `@/` alias,
`import type`, `cva`/`cn()`, Prettier, don't edit `src/components/ui/**` in

## Backend contract (verified — do not re-derive)

Verified against `api/jwks.go`, `internal/signing/provider.go`,
`jwk_parse.go`, `os_store.go`, `self_pki.go`, `external_pki.go`, and the router
wiring in `api/api.go`.

| Path | Method | Auth |
|---|---|---|
| `/jwks.json` | GET | **Public** — root router, no auth middleware |
| `/api/v1/jwks/rotate` | POST | **Admin**, checked inside the handler |

- `api/jwks.go:16` registers the GET on the `JWKS` subrouter, built at
  `api/api.go:150-151` from `api.rootRouter.NewRoute().Subrouter()` with only
  `CORSMiddleware` and `SecurityHeadersMiddleware`. **The path is literally
  `/jwks.json` at the origin root — not under `/api/v1`.** Every other API
  module in this app prefixes `/api/v1`; this one must not.
- `api/jwks.go:19` registers the rotate on `ApiRoot` (`/api/v1`) with the full
  middleware chain. The admin gate is in the handler, not middleware:
  `api/jwks.go:43-46`, `common.HasAnyRole(c.Claims.Roles, model.RoleAdmin)` →
  403 `"admin role required to rotate signing keys"`. `PolicyMiddleware` does
  not match `/jwks/rotate` (`internal/middleware/middleware.go:407-428` — `jwks`
  is not `keys`), so the handler check is the only gate.
- These are the **only two** JWKS routes. There is no key-metadata GET, no
  delete, no revoke.

**GET `/jwks.json` response** — `{"keys": [...]}` (`api/jwks.go:99-109`).
Per-key fields, from `internal/signing/jwk_parse.go`:
- RSA (`:12-21`): `kty` (`"RSA"`), `use` (`"sig"`), `alg`, `kid`, `n`, `e`.
- EC (`:24-42`): `kty` (`"EC"`), `use` (`"sig"`), `alg`, `kid`, `crv`
  (`"P-256"` | `"P-384"` | `"P-521"`, `:56-67`), `x`, `y`.
- **Nothing else.** No `created_at`, no `exp`, no `status`/`active`, no
  `key_ops`, no `x5c`.
- `Cache-Control: public, max-age=3600` (`api/jwks.go:36`). **No ETag, no
  Last-Modified, no conditional-request handling** anywhere in `api/`.

**Key count depends on `jwt.key_source`:** `os_store` always 1
(`internal/signing/os_store.go:132`), `external_pki` always 1
(`external_pki.go:51`), `self_pki` 1 **or 2** — active plus previous, and only
while `time.Now().Before(overlapUntil)` (`self_pki.go:86-104`), active first.
**No field distinguishes active from previous**, so the UI cannot label them
from the document alone; ordering is the only signal and it is not part of any
contract.

**POST `/api/v1/jwks/rotate` success** — exactly three fields,
`{"status": "ok", "new_kid": "...", "overlap_until": "<RFC3339>"}`
(`api/jwks.go:72-76`; matches `JWKSRotateResponse`,
`docs/api-specification.yaml:4732-4746`).

**Rotation is only supported for `jwt.key_source: self_pki`.** The handler type-
asserts `provider.(signing.RotatableProvider)` and returns **HTTP 400** with id
`api.jwks.rotate_not_supported` and message
`"key rotation is only supported for the self_pki key source"` for `os_store`
and `external_pki` (`api/jwks.go:55-60`). Only `self_pki` implements `Rotate()`
(`internal/signing/self_pki.go:108-153`); `external_pki.go:17` states operators
replace the key and restart.

**⚠ Two different error envelopes on the two routes.** `getJWKS` writes a bare
`{"error": "..."}` (503 `"signing provider not available"` at `api/jwks.go:26`,
500 `"failed to build JWK set"` at `:32`) — the spec calls this
`SimpleErrorResponse`. `rotateJWKS` uses the standard `common.AppError` envelope
(`api.jwks.provider_unavailable` 503, `api.jwks.rotate_not_supported` 400,
`api.jwks.rotate_failed` 500). The foundation's `ApiError` mapping assumes the
`AppError` shape, so the GET needs its own error path.

**What rotation does to the old key** (`self_pki.go:108-153`): a new ECDSA P-256
key is generated and inserted as a **new** DB row (`:135`) — the old row is
neither deleted nor soft-deleted, so material accumulates. The previous key is
retained for validation only until `overlapUntil` (`:96`), and only **one**
previous key is held — a second rotation inside the window discards the first
immediately. Rotation state (`previousKey`, `overlapUntil`) is **in-memory only
and lost on restart** (`loadOrGenerate`, `:156-190`), so a restart inside the
window invalidates tokens signed with the prior key.

**Audit trail:** both success and failure write an entry with
`Action: "jwks_rotate"`, `ResourceType: "signing_key"`, `ResourceID: <newKID>`
(empty on failure), `Source: "api"`, `Outcome: "success"|"failure"`
(`api/jwks.go:82-96`). This is the **only** source of rotation history — see
Task 4.

**No CLI exists.** `grep -rni "jwks" cmd/` returns zero hits.
`cmd/keys/rotate.go` rotates vault data keys and `vault-webhook --rotate-secret`
rotates a webhook HMAC secret; neither touches the signing key. So this screen
becomes the only practical operator surface besides raw curl — worth stating in
the UI.

**Config keys** (all viper): `jwt.key_source` (default `os_store`,
`internal/signing/provider.go:50-53`), `jwt.key_cn` (`os_store` only, `:57-60`),
`jwt.rotation_overlap` (default 1h, `self_pki` only, `:67`),
`jwt.signing_key_file` (`external_pki` only, `:71`). **There is no
`jwt.algorithm`** — the algorithm is determined entirely by the key source.

## Self-Review

- Both real routes have a task; no key-metadata GET, delete, or revoke endpoint
  is invented, and the absence of a `created_at` is worked around through the
  audit log (Task 4) rather than fabricated.
- The unversioned public `/jwks.json` path is pinned by a test (Task 1) — the
  single highest-probability copy-paste error in this epic.
- The two divergent error envelopes are both handled, so a 503 from the GET
  does not degrade into an empty key list.
- Rotation support is discovered from the server's 400, not from a guessed
  config flag the client has no way to read — consistent with Epic 03's
  OCT/HSM handling.
- Active-vs-previous is not claimed anywhere, because the JWK set genuinely
  does not say; a negative test enforces it.
- The epic is fenced off from Epic 03 in the goal, the nav label, and an
  on-screen alert, so "keys" never collapses into one concept.
