End-to-end walkthrough

1
Start the server ~10s
Run from source. The server reads .rocketvault.yaml from the working directory.
bash
go run main.go serve
export BASE=http://localhost:8774
curl -s $BASE/api/v1/health/live   # → {"status":"OK"}
2
Bootstrap the first admin ~30s
CLI-only, one-time. Uses the bootstrap_token from your config. The response includes a TOTP secret — register it before step 3.
bash
go run main.go users admin \
  --admin-username admin --admin-password admin123 \
  --bootstrap-token <your-bootstrap-token>
# stdout → TOTP Secret: otpauth://totp/...&secret=<BASE32>
Register TOTP now

Scan the otpauth:// URL in Google Authenticator, Authy, or 1Password. Or mint codes on the CLI: oathtool --totp --base32 <BASE32>. Every login requires a TOTP code.

3
Log in and capture the JWT ~15s
Returns a short-lived access token and a refresh token. Store the access token in $TOKEN.
POST /api/v1/users/login Authenticate, get a JWT
TOKEN=$(curl -s -X POST $BASE/api/v1/users/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"admin123","totp_code":"123456"}' \
  | jq -r .token)
rocketvault users login \
  --username admin --password admin123 --totp-code 123456
{
  "token": "<redacted-jwt>",
  "refresh_token": "<redacted-jwt>",
  "user_id": "f99945c6-ded6-4d6d-96be-7a10a1fbe6fe",
  "username": "admin",
  "roles": ["admin"]
}
4
Store a secret ~10s
Secrets are encrypted at rest with AES-256-GCM. Only the owner or admin can read them without a vault role assignment.
bash
SECRET_ID=$(curl -s -X POST $BASE/api/v1/secrets \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name":"DB_PASSWORD","value":"s3cret"}' | jq -r .id)
echo $SECRET_ID
5
Create a service account and grant read access ~30s
Service accounts are machine identities — no TOTP, authenticate via OAuth2 client credentials. The client_secret is shown only once.
bash
SA=$(curl -s -X POST $BASE/api/v1/service-accounts \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name":"my-app","description":"reads DB_PASSWORD"}')
CLIENT_SECRET=$(echo "$SA" | jq -r .client_secret)
SA_ID=$(echo "$SA" | jq -r .id)

curl -s -X POST $BASE/api/v1/vaults/default/role-assignments \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"principal":"'"$SA_ID"'","principal_type":"service_account","role":"Key Vault Secrets User"}'
Why a vault role assignment?

Since v4.0.0, granting access to secrets, keys, or certificates goes through a vault role assignment, not an access policy — access policies now only add explicit-deny exceptions. Key Vault Secrets User in the default vault lets my-app read every secret there; a service account with no role assignment can authenticate but read nothing — principle of least privilege.

6
Consume the secret as your app ~15s
Exchange client credentials for a bearer token, then read the secret. This is the pattern your app repeats at runtime.
bash
APP_TOKEN=$(curl -s -X POST $BASE/api/v1/oauth2/token \
  -u "my-app:$CLIENT_SECRET" \
  -d "grant_type=client_credentials" | jq -r .access_token)

curl -s $BASE/api/v1/secrets/$SECRET_ID \
  -H "Authorization: Bearer $APP_TOKEN" | jq .value
# → "s3cret"

Before You Begin

Prerequisites

  • Go 1.24+ to build and run the server (go run main.go serve).
  • curl and jq for the API examples; oathtool to mint TOTP codes without a phone.
  • A populated .rocketvault.yaml (the only config the server reads). Key settings: server.listen_addr (default :8774), the bootstrap token, and jwt.*.
  • The server running and an admin bootstrapped (see Quick Start above).

Conventions in this manual

  • $BASE is http://localhost:8774; $TOKEN is an admin JWT from login.
  • Example responses are captured from a live server; secret values, key material, and tokens are shown as <redacted> placeholders.
  • Each operation shows tabs — cURL, CLI, and a real Response where applicable.

Installation & First Run

What it is

RocketVault runs as a single Go binary. The server reads exactly one config file, .rocketvault.yaml, from the working directory or --config.

Run from source
go run main.go serve
go run main.go serve --config /path/custom.yaml
Verify it is up
export BASE=http://localhost:8774
curl -s $BASE/api/v1/health/live
Config notes

The server listens on :8774 by default (see server.listen_addr). Set environment: development or production to select DB pool defaults.

Mental Model

What it is

RocketVault is a self-hosted, open-source alternative to Azure Key Vault, written in Go. It manages secrets, RSA/ECDSA keys, and X.509 certificates through a REST API and a Cobra CLI, with JWT+TOTP authentication and RBAC.

Secrets, keys, and certificates are encrypted at rest with AES-256-GCM. The CLI calls the service container directly, bypassing the HTTP layer.

Bootstrap — First Admin User

What it is

A one-time bootstrap token creates the first admin without authentication. After use, the token is consumed. The response returns a TOTP secret you must register in an authenticator app — every login requires a TOTP code.

When to use it

  • Fresh install — no admin user exists yet.
  • Emergency recovery — locked out with no active admin sessions.

Bootstrap is a CLI-only operation — there is no HTTP endpoint.

bash
rocketvault users admin \
  --admin-username admin \
  --admin-password admin123 \
  --bootstrap-token <token>
Register TOTP before logging in

Register the returned totp_qr_url in your authenticator app. You can mint codes with oathtool --totp --base32 <secret>.

OIDC / SSO Login

What it is

An additional login path via any standards-compliant OpenID Connect provider (Okta, Keycloak, Entra ID, etc.) — an external identity provider authenticates the principal, then RocketVault issues the exact same JWT/refresh-token pair local login does. Local username/password/TOTP login (see Authentication) is completely unaffected and stays available.

When to use it

  • Centralize authentication behind an existing corporate identity provider instead of maintaining a separate username/password/TOTP per person in RocketVault.
  • Users with an active SSO session already open in their browser get an instant login with no prompt at all.

Configuration

oidc:
  enabled: true
  issuer_url: "https://idp.example.com"
  client_id: "rocketvault"
  client_secret: "<from your IdP's client registration>"
  redirect_url: "https://vault.example.com/api/v1/oidc/callback"
  scopes: ["openid", "profile", "email"]
  # Optional: trust a private/internal CA for the issuer's TLS certificate,
  # instead of the SSL_CERT_FILE environment variable.
  ca_cert_path: "/etc/rocketvault/idp-ca.pem"
Disabled by default

oidc.enabled defaults to false. When unset, GET /oidc/login and GET /oidc/callback return 503 and the server never attempts a network call to the issuer at startup. If oidc.enabled is true but the issuer is unreachable, issuer_url is malformed, or ca_cert_path fails to load, the server logs a warning and starts anyway with OIDC left unavailable — same 503, different cause. Check the startup log for Failed to initialise OIDC service to tell the two apart.

First login vs. repeat login

  • The first login for a given IdP subject creates a new user with the least-privilege roles: ["user"] and zero vault access — an admin must grant a vault role separately, same as any other user (see Vault RBAC).
  • Every later login for that same subject reuses the existing user row — it does not create a duplicate, and it does not reset the roles an admin has since changed.
  • RocketVault calls the provider's userinfo endpoint on every login (one extra round trip to the IdP) and uses it to fill in whichever of name/email/preferred_username the ID token left out (common with some providers) — falling back further to the IdP's raw subject claim if userinfo leaves them empty too.

Logging out

There is no OIDC-specific logout endpoint — an OIDC-authenticated user logs out exactly like a local-login user, via the same session-revocation endpoints (see Authentication), since both share the identical JWT/session machinery.

# find your own session id (the "jti" claim in your token)
echo $TOKEN | cut -d. -f2 | base64 -d | python3 -m json.tool
DELETE /api/v1/users/sessions/{id} JWT Log out this session
curl -s -X DELETE $BASE/api/v1/users/sessions/<jti> -H "Authorization: Bearer $TOKEN"
DELETE /api/v1/users/sessions JWT Log out of every session
curl -s -X DELETE $BASE/api/v1/users/sessions -H "Authorization: Bearer $TOKEN"

Revocation takes effect immediately — the very next request with that token is rejected (401), even though the JWT itself is still cryptographically valid and unexpired.

Logging out does not end the IdP session

Revoking a RocketVault session only revokes RocketVault's own session. RocketVault does not call the IdP's end_session_endpoint (no RP-initiated logout is implemented), so a user with an active SSO session in their browser can hit GET /oidc/login again immediately afterward and be silently re-authenticated with no prompt. A full logout requires separately ending the session at the identity provider.

See also: Authentication (session revocation), Vault RBAC (granting access to a new OIDC user)

JWT Signing & Key Sources

What it is

JWTs are signed asymmetrically and verifiable via JWKS at /jwks.json. Three providers control where the signing key lives, set by jwt.key_source.

ProviderStorageAlgorithmRotation
os_store (default)OS keychain, PEM-file fallbackRS256No
self_pkiRocketVault's own encrypted DBES256Yes (runtime)
external_pkiPEM from file or env varRS256/ES256No
GET /jwks.json Public JWK set (no auth)
curl -s $BASE/jwks.json | jq '.keys[0].alg'
{
  "keys": [{
    "kty": "RSA", "use": "sig", "alg": "RS256",
    "kid": "9d1c755f04ddbcfc",
    "n": "<base64url-modulus>", "e": "AQAB"

}
POST /api/v1/jwks/rotate JWT · admin Rotate (self_pki only)
curl -s -X POST $BASE/api/v1/jwks/rotate -H "Authorization: Bearer $TOKEN"
Why this works

With os_store the key lives in the OS keychain and rotation returns 400 — only self_pki supports runtime rotation. Headless hosts fall back to ~/.local/share/rocketvault/jwt-signing.pem (mode 0600).

When to use it

Vault RBAC & Role Assignments

What it is

Since v4.0.0, vault data-plane authorization matches Azure Key Vault's own RBAC model. A role assignment grants a principal — a user or service account, always tenant-global — one of eleven built-in roles, scoped to exactly one vault. The assignment carries the vault boundary, not the identity: the same user can be a Key Vault Reader in staging and a Key Vault Administrator in prod. Object ownership (created_by) is retained purely as audit provenance and is never consulted for an access decision.

When to use it

  • Grant access to everything of one kind — all secrets, all keys, or all certificates — within a single vault.
  • A newly created vault starts with zero role assignments. Nobody but a global admin can read or write objects in it until someone grants a role.

bash
# List the built-in roles and what each one grants (no auth required)
rocketvault vault-access roles
Out-of-scope is 404, not 403

Requesting a resource that exists in another vault returns 404 Not Found — the two are indistinguishable by design, so a caller can't use the status code to fingerprint objects it holds no role over. 403 means: authenticated but no role assignment grants the action in this vault, a disabled vault, or a resource outside its validity window.

Delegating role-assignment management

Granting, revoking, or reading role assignments all require the admin account role, a vault-scoped vaults:manage access policy, or the Key Vault Data Access Administrator role in that vault — listing a vault's assignments discloses who holds which role there, so it is gated identically to changing them. Grant a non-admin operator that role to let them manage access for one vault without making them a global admin: rocketvault vault-access grant alice --role "Key Vault Data Access Administrator" --vault prod --username admin --password admin123 --totp-code 123456.

Upgrading from a pre-4.0.0 install

Run rocketvault vaults preview-migration before starting the new binary — it prints every role assignment the upgrade would create without writing anything. The one-time backfill derives assignments from object ownership, the legacy global admin role, and any pre-existing vault-scoped role_assignments row. It does not see access policies created via the old allow-grant API — cross-reference SELECT DISTINCT principal_id, resource_type, operation, vault_id FROM access_policies WHERE effect='allow' against those sources and grant any gaps manually, before or immediately after upgrading.

DELETE /api/v1/vaults/{vault_name}/purge JWT Permanently purge a vault
curl -s -X DELETE $BASE/api/v1/vaults/prod/purge -H "Authorization: Bearer $TOKEN"
rocketvault vaults purge prod --username admin --password admin123 --totp-code 123456
Notes
Requires the Key Vault Purge Operator role in the target vault — a role assignment, not an access policy, since this is a vault data-plane route. Unlike the CLI's vaults purge command, the HTTP endpoint has no admin bypass: a global admin without an explicit grant is denied, matching real Azure Key Vault semantics (vault purge is a separate role from Key Vault Administrator). Refuses the default vault and any vault with purge protection enabled (400 either way). 404 if the vault doesn't exist.

Access Policies

What it is

An access policy is a rule for one (principal, resource type, operation) triple, optionally scoped to a vault (vault_id: null means global). Since v4.0.0 policies are evaluated first, as an explicit-deny override, ahead of every role decision — a deny always wins and can never be outvoted by a role grant. On the three vault data-plane resource types (secrets, keys, certificates) an allow-effect policy no longer grants anything by itself; grant access with a vault role assignment instead. allow still functions for the one remaining resource type, vaults + manage, which gates vault administration.

Breaking change in v4.0.0

Before v4.0.0, an allow access policy was itself sufficient to grant access. A principal whose only access came from an allow policy on secrets, keys, or certificates loses that access at upgrade — and is invisible to the automatic role-assignment backfill. See the upgrade callout in Vault RBAC & Role Assignments.

When to use it

  • Carve out a narrow exception under a broader role grant — e.g. effect: deny one specific secret for a principal who otherwise holds Key Vault Secrets Officer in that vault.
  • Gate vault management (resource_type: vaults, operation: manage) with an allow policy — the one place allow still grants directly.
  • To grant read or write access to secrets, keys, or certificates, use a vault role assignment, not an access policy.

  -d '{"principal_id":"<id>","principal_type":"service_account","resource_type":"secrets","operation":"get","effect":"deny","vault_id":"<vault-id>"}'
{
  "id": "<uuid>",
  "principal_id": "<uuid>",
  "principal_type": "service_account",

Account Roles & Permissions

What it is

Every user account carries exactly one global role. It gates coarse, account-level operations — user management, and, for admin, vault administration and flat-route access to every resource type. This is distinct from vault role assignments, which grant fine-grained, per-vault access via the eleven Azure built-in roles.

The old vault-scoped role names are deprecated

RocketVault v0.2.0 shipped a first-cut vault-scoped role vocabulary — vault-reader, secrets-officer, crypto-user, and so on. Since v4.0.0 those names are legacy: vault-access grant refuses to hand one out, and holding one grants zero data-plane access. Use one of the eleven Azure built-in roles instead.

The six roles

RoleSecretsKeysCertificatesUsersSystem
adminfull CRUD + listfull CRUD + listfull CRUD + listfull CRUD + listmanage vaults + system
userread, listread, listread, list——
secrets_managerfull CRUD + list————
crypto_manager—full CRUD + list———
certificate_manager——full CRUD + list——
service_accountread, listread, listread, list——

Notes

  • "Full CRUD" means create, read, update, and delete.
  • user and service_account are read-only across all three resource types on flat routes. They differ only in intent: user is a human login, service_account is a machine identity. Admins create resources and grant finer, per-vault access via vault role assignments.
  • A manager role grants full CRUD on its one resource type and nothing on the others. secrets_manager cannot even read keys or certificates.
  • Unknown roles get zero permissions. The check denies by default.

OAuth2 Service Accounts

What it is

A service account is a machine identity that authenticates via OAuth2 client-credentials flow — no TOTP. Service accounts are read-only consumers: they retrieve secrets/keys/certs an admin granted them via access policies.

When to use it

  • CI/CD pipelines, apps fetching config at runtime, service-to-service secrets, scheduled jobs.
  • Any automated caller — prefer service accounts over human user credentials for machine access.
Why no TOTP?

TOTP requires a human to read a time-based code. Service accounts use a long client secret instead — machine-readable, rotatable, and revocable without user involvement. The tradeoff is that the secret must be stored securely by the caller (e.g. in a CI secret store).

What the isolation model is — and is not

The precise description of RocketVault's model is multi-vault isolation with delegated per-vault administration. It is not self-service multi-tenant SaaS, and the distinction decides whether the product fits your deployment. Read this section before describing a RocketVault instance as "multi-tenant" to anyone evaluating it.

What you genuinely get:

  • Real isolation. Secrets, keys and certificates are scoped by vault_id in the database query itself, not filtered in application code after the fact.
  • Delegated per-vault administration. The Key Vault Data Access Administrator role lets someone manage grants and revokes within their own vault, without global admin rights and without reaching any other vault.
  • Independent per-vault RBAC. One principal can hold different roles in different vaults at once; access in vault A implies nothing about vault B.
  • No cross-vault leakage. A member of vault A cannot enumerate vault B, or learn that it exists, without a separate grant.
  • Per-vault request budgets. One vault's traffic cannot exhaust another's — see Rate Limiting.

What is not supported today:

GapWhat it means in practice
No self-service vault provisioning Creating or updating a vault requires a global vaults:manage grant, not one scoped to a vault. A tenant administrator cannot create their own vault — a platform operator must provision it for them. This is the blocker for managed-service-provider and hosting-provider deployments where customers expect to create vaults without raising a ticket.
No tenant entity — vaults are flat Nothing groups several vaults under one customer or organisation; the vault is the only isolation unit. So there is no way to express "revoke this contractor from all of customer X's vaults", no reporting that rolls up per customer, and no unit to attach billing or quota to.
No per-vault metering Per-vault rate limiting exists, but request volume, storage consumption and billing are not measured per vault beyond a Prometheus counter of throttling rejections.
If you need full tenant separation today

Run one RocketVault instance per tenant. Self-hosting makes this cheap — a single Go binary with SQLite or Postgres — and it gives stronger isolation than any in-product namespace feature would, at the cost of managing more instances. The multi-vault model above is the right fit when one platform team runs the instance and provisions an isolated vault per internal team or customer.

These gaps are tracked as high-priority roadmap items. Note they are not Azure Key Vault parity gaps: Azure has no tenancy concept inside the vault service either — in Azure, tenancy lives in the platform above it (subscription and Entra ID tenant).

21. Rate Limiting

What it is

Two independent limits protect the API, and a request must pass both. Per-IP limits stop a single noisy host; the per-vault limit stops a single noisy tenant whose traffic is spread across many hosts. All three are continuously-refilling token buckets, so steady traffic is never blocked by a fixed-window boundary.

LimitCounted perDefaultConfig key
All API endpointsclient IP300 req/minrate_limit.default
Auth (/login, /refresh, /oauth2/token)client IP5 req/minrate_limit.auth
All authenticated API endpointsvault600 req/minrate_limit.per_vault

Exceeding any limit returns 429 Too Many Requests. Each limit reports its own response headers, so a client can tell which ceiling it hit:

HeaderMeaning
X-RateLimit-Limit / -Remaining / -ResetThe per-IP budget.
X-RateLimit-Vault-Limit / -Remaining / -ResetThe per-vault budget.

Per-vault limiting — the noisy-neighbour guard

Without it, one busy vault can spend the whole instance's request budget and degrade every other vault. The per-vault bucket makes each vault's capacity its own: traffic against vault A can never consume vault B's budget. This matters most when you host an isolated vault per team or per customer — see Multi-Vault.

Three behaviours are worth knowing before you tune it:

  • Health probes are exempt. /health, /health/ready, /health/live and /health/database resolve no vault, so they are never counted — otherwise a frequent liveness probe would drain the default vault's budget and throttle real traffic.
  • Routes with no vault of their own count against the default vault. That covers vault-management routes (/vaults/…) and the legacy flat resource paths (/secrets, /keys, /certificates). Heavy use of those shares a budget with the default vault's own traffic.
  • Rejected requests still count. The limit is applied before the authorization check, so a caller who is denied (403) still spends vault budget. This is deliberate — it means an unauthorized client hammering a vault is throttled rather than being handed unlimited free rejections.

The per-vault limit runs after authentication, so it is a tenant-fairness control, not a denial-of-service control. Unauthenticated floods are the per-IP limiter's job.

Seeing who is being throttled

With monitoring.enable_metrics: true, every per-vault rejection increments a Prometheus counter labelled with the vault, so you can identify the noisy tenant rather than just observing that something is being throttled:

rocketvault_vault_rate_limit_exceeded_total{vault="<vault-uuid>"}

Rejections are also written to the audit log under the vault_rate_limit operation.

22. Performance Internals

What it is

Two tunable subsystems run transparently. Caching: an in-memory key cache (key_cache.*, default 60s TTL / 500 entries) and a secret cache speed up reads. Retry: database and external-service operations use exponential backoff with jitter and a circuit breaker (retry.*).

These are configuration-tuned rather than operated directly — defaults are production-safe. Adjust only with measurement. The key_cache and retry blocks in §4 Configuration list the tunable keys.

25. Consuming Secrets in Your Application

What it is

Applications retrieve secrets at runtime using a service-account OAuth2 token, so secrets never live in code or config. Three integration styles are supported.

Options

Go (vaultclient)
client, _ := vaultclient.New(vaultclient.Config{
  URL:          "http://localhost:8774",
  ClientID:     "my-app",                 // SA name
  ClientSecret: os.Getenv("VAULT_CLIENT_SECRET"),
  Secrets: []vaultclient.SecretMapping{
    {Name:"DB_PASSWORD", UUID:"<uuid>"}},
})
secrets, _ := client.GetMany(ctx, []string{"DB_PASSWORD"})
Shell / direct HTTP
# Get token
curl -X POST $BASE/api/v1/oauth2/token \
  -d "grant_type=client_credentials&client_id=my-app&client_secret=$SEC"
# Fetch a secret by UUID
curl $BASE/api/v1/secrets/<uuid> -H "Authorization: Bearer <access_token>"
Note

VAULT_CLIENT_SECRET must come from an environment variable, never a config file. The server's own vault_client.client_id must be empty.

Appendix D — Security Checklist

  • VAULT_CLIENT_SECRET in env vars only — never a config file or git.
  • Server's vault_client.client_id is empty (the server must not call itself).
  • Each application has its own least-privilege service account.
  • Rotate service-account secrets periodically (/service-accounts/{id}/rotate).
  • JWT signing key persists across restarts (keychain or 0600 PEM) — never in /etc/ssl/certs.
  • Audit retention configured; verify integrity_ok on audit queries.
  • Purge protection enabled for sensitive vaults.
  • Vault role assignments reviewed per vault (rocketvault vault-access list --vault <name>) — no principal holds more than it needs.
  • Before upgrading to v4.0.0+, ran rocketvault vaults preview-migration and checked for allow-only access policies invisible to the backfill (Vault RBAC).
