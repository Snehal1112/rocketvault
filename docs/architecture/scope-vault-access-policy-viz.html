Scope, Vault & Access Policy in RocketVault

How a request gets from "here's a JWT" to "yes/no, and why" — the three authorization primitives and how they compose.

The practical order operators actually use these pieces in: bootstrap an admin, create a vault, create a user, grant that user a vault-scoped role, optionally lock something down with an explicit policy, then let the user operate. Each step below is a real CLI command.

A vault is a named container and isolation boundary for secrets, keys, and certificates — model.Vault. Every deployment ships a reserved default vault (DefaultVaultID = 00000000-0000-0000-0000-00000000efa1) so single-vault use needs no extra setup. Resources are unique per (vault_id, name), so two vaults can each have their own secret named db-password.

Two ways a request reaches a vault

/api/v1/vaults/prod-payments/secrets/{id} resolves by path → prod-payments
/api/v1/secrets/{id} legacy flat route, no vault in path → default
Visibility model: any caller authorized for a vault sees everything in it — access is governed by vault access policies + RBAC, not per-user object ownership. This is uniform across secrets, keys, and certificates: a "vault member" isn't scoped down to only the items they personally created.
Resolution middleware: VaultResolutionMiddleware reads the {vault_name} path variable, falls back to default if absent, and injects the resolved vault ID into the request context — right after authentication, before any policy check runs.

model.Scope is a value object every repository and service call carries to say how an operation is authorized. It replaced a family of vault-suffixed and owner-suffixed method pairs — the scope now travels as data instead of being baked into a method name. Its zero value is deliberately invalid, so an uninitialised scope fails closed rather than silently granting access.

ScopeInvalid
zero value
The default when a Scope is never explicitly built. Validate() always rejects it — repositories refuse to run a query with this scope.
ScopeVault
any vault member
Any member of vaultID may act. The everyday scope for vault data-plane routes — /vaults/{name}/....

No predicate at all. Reserved for the vault cascade delete, backup/restore, and the rotation scheduler — never derived from a caller's HTTP request.

Validate() — the fail-closed gate

Every repository entry point calls Scope.Validate() before building a query:

→OK

Note what actorID is not: it's recorded on every scope for audit attribution, but it never functions as an access predicate — only vaultID (ScopeVault) or ownerID (ScopeOwner) restrict what a query can see.

Why the order matters

Step 1 runs first and can only ever deny. An explicit Deny row in access_policies — vault-specific or global (vault_id IS NULL) — always wins, before any role grant is even consulted. Step 2 is deny-by-default: for vault data-plane routes (secrets/keys/certs operations), silence is not access — the caller must hold a role_assignments row in that specific vault granting the mapped Azure data action, via RoleAssignmentService.HasDataAction. Non-data-plane routes (vault management, role-assignment management, users, audit) skip step 2 entirely and fall through to step 3, where the handler itself does the check.

access_policies plays two roles at once: it's where explicit manual grants/denies live, and it's also the table legacy roles used to expand into. Azure built-in roles are evaluated directly from role_assignments instead of being materialized into access_policies rows — avoiding a second, driftable source of truth for the same grant.
