The version number is provisional and may change before tagging.

This release hardens login and rate limiting after the 2026-09-30 audit of api/ (issue #46). Full detail: .claude/known-bugs.md (B85, with the follow-ups B91 to B93). It also contains a minimal fix of B90 (#56), which stays partly open.

What changed

  • One client-IP resolver. server.trusted_proxies (default empty) lists the reverse proxies whose X-Forwarded-For and X-Real-IP headers are trusted. Every consumer (rate limits, request logs, audit rows) goes through ClientIPResolver. It walks X-Forwarded-For from the right and returns the first hop that is not a trusted proxy. X-Real-IP is read only when the trusted proxy sent no X-Forwarded-For. An unreadable hop falls back to the peer address. An invalid trusted_proxies entry is logged and the whole list is ignored, so nobody is trusted.
  • IPv6 clients are limited per /64. The audit IP stays the full address.
  • Bounded rate-limiter maps. Buckets idle for 2 minutes are dropped (lazy sweep at most once a minute) and each limiter holds at most 100000 entries. See the residual risk below.
  • Per-account failed-login backoff. 5 free failures, then a wait of 2s that doubles per failure up to 15 minutes; a counter whose last failure is 24 hours old is forgotten. The key is the exact username (a SHA-256 key for names over 64 bytes). Every identity failure exit counts: unknown user, wrong password, missing TOTP secret, wrong or malformed code, replayed code and claim failure. A successful login resets the counter. A throttled login answers HTTP 429 with Retry-After, with the same body for known and unknown usernames. If the counter table cannot be read, login proceeds and a warning is logged (the per-IP limiter still applies).
  • Constant-time rejection. Unknown users, unknown, disabled or expired OAuth2 clients and accounts whose stored hash is not usable bcrypt (OIDC accounts, the system user, a bad OAuth2 client secret hash) now spend one bcrypt compare, so timing does not reveal which names exist.
  • /oauth2/token reads credentials from the body only. client_id, client_secret and grant_type in the query string are ignored.
  • /config is rate limited (per client IP, rate_limit.default).
  • client_id in OAuth2 audit rows is sanitised: control characters and invalid UTF-8 are dropped and the value is capped at 255 bytes.
  • Database breaker, minimal B90 fix. The shared database circuit breaker no longer counts client outcomes (bad credentials, bad tokens, throttled logins) or cancelled requests as database failures. A client error in a half-open trial releases its slot. Without this the new 429 could not be observed under the default breaker settings. B90 stays partly open (see .claude/known-bugs.md).

Breaking changes

  1. Forwarded headers are no longer trusted by default. Behind a reverse proxy, every client now shares the proxy's address until server.trusted_proxies is set: they share one rate-limit bucket (the 5 req/min auth budget included) and audit rows show the proxy's address.
  2. /oauth2/token ignores query-string credentials. A client that sends client_secret or client_id in the query now gets 401, and one that sends grant_type there gets 400. Send them in the form body or HTTP Basic.
  3. A sixth consecutive failed login for one account returns 429 with Retry-After for a growing delay.

Upgrade procedure

  1. Behind a reverse proxy (Railway, Fly, nginx, a load balancer): set server.trusted_proxies to the proxy's address or range. This is required, not optional. Example:

    yaml
    server:
  trusted_proxies:
    - "10.0.0.0/8"

    Requirements and pitfalls:

    • The trusted proxy must append to or overwrite X-Forwarded-For. X-Forwarded-For is preferred over X-Real-IP; a proxy that sets only X-Real-IP while passing the client's own X-Forwarded-For lets that client choose its IP.
    • A hop that carries a port (for example 1.2.3.4:5678, as some Azure gateways send) is unreadable, so the resolver falls back to the peer and all clients share one bucket.
    • The value must be a YAML list. A single comma-separated string is read as one invalid entry and the list is ignored without a startup failure (an error is logged).
    • .rocketvault.docker.yaml.tmpl, used by docker, Fly and Railway, hardcodes trusted_proxies: [] and has no environment variable for it yet, so edit the rendered template for those targets.

  2. Direct deployments: no action. The headers are ignored.

  3. The login_failures table is created automatically at startup on SQLite and Postgres (no manual step).

  4. Clients of /oauth2/token that put credentials in the query string must move them to the body or Basic auth.

Schema

New table login_failures (username, failures, last_failure_at, with an index on last_failure_at). It is dual-written in createOptimizedSchema and migrateSchema and is included in the backup table order.

What did not change

rate_limit.default, rate_limit.auth and rate_limit.per_vault keep their values, and the per-vault limiter is untouched. /jwks.json is still not rate limited (B93).

Known limitations and operator warnings

  • /64 granularity. A provider allocation of a /56 or /48 can still occupy many buckets.
  • Limiter flood residual. Once a limiter holds 100000 live keys, a new key evicts one. An attacker presenting more than 100000 distinct keys within 2 minutes (distinct IPv4 addresses or /64 prefixes) can reset a quieter client's bucket. That needs a distributed attacker; the per-account backoff still applies.
  • Backoff can slow a known user. Anyone can slow the logins of a known username (administrator accounts included) by failing 5 times. The delay is capped at 15 minutes and the real user can log in once it passes. This is accepted.
  • Activity oracle. A success resets the counter, so probing a name can reveal that someone logged in successfully since the last probe.
  • Table growth. login_failures grows with sprayed usernames. There is deliberately no hard cap, because evicting rows would let an attacker flush a victim's counter. Rows older than 24 hours are pruned on each recorded failure. Monitor the table size.
  • Concurrent burst. The throttle check and the failure record are separate steps, so simultaneous attempts at the end of a window can each get a guess (B92; follow-up: atomic reservation).
  • Legacy bcrypt hashes. Hashes created at cost 10 (before the cost increase) verify faster than the dummy compare, which reveals that an account has a legacy hash, not whether an account exists.
  • Unknown usernames cost a bcrypt compare each, bounded only by the per-IP limiter.
  • Login logging. The raw login username is logged unescaped (B91).
