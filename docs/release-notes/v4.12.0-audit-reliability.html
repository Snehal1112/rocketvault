v4.12.0 — Audit reliability

The version number is provisional and may change before tagging.

The audit log now fails closed for critical operations, keeps one hash chain across any number of replicas, and names the row where verification fails. It fixes § B98 (GitHub #64), § B104, § B105 and § B108.

Breaking changes

  1. Critical operations are refused when their audit row cannot be written. Each one now writes an attempt row first and runs only if that write succeeds. If the audit store is unavailable the API answers 503 with the body audit unavailable, and nothing changes. The operations are: login and token issue and refresh (including service accounts and OIDC), JWKS rotation, secret, key and certificate exports, purges (including the scheduled soft-delete purge and the audit retention purge), user and vault delete, key create, import, rotate, delete, wrap and unwrap, secret rotation, role grant and revoke, and signing key generation under self_pki. After the operation runs, a second row with the same action records success or failure. Scheduled rotation and purge skip the item and retry on the next tick. Events that are not critical stay best effort.
  2. self_pki can fail startup. On first boot, or after the signing key is regenerated because it could not be decrypted, the provider writes a signing_key_generate row before it stores the key. If that write fails, the server does not start (audit unavailable). Loading an existing key is unchanged.

What changed

  • Chain seq and head table. audit_logs has a new seq column (unique index) and a new single-row audit_chain_head table holds the last seq and hash. Each write locks the head row, assigns the next seq and inserts in one transaction, so replicas no longer fork the chain and a failed read no longer resets it (§ B104, § B105). GetLastHash and the in-process mutex are removed.
  • New integrity fields. GET /api/v1/audit/logs, the CLI and the MCP query_audit_log tool report integrity_break_seq and integrity_break_reason (gap or hash_mismatch) when integrity_ok is false. Both fields are absent while the chain verifies. A filtered query can still report a false break (§ B106).
  • New metric. rocketvault_audit_write_failures_total{action} counts audit rows that could not be written. Suggested alert: increase(rocketvault_audit_write_failures_total[5m]) > 0.
  • Outcome for denied rows. Rows written through the logger now get an outcome from their status: success, failure, denied or warning (§ B98). rocketvault audit logs --outcome denied selects refusals, which fixes the workaround in the v4.11.0 upgrade notes.
  • DeleteUser records the acting admin. The delete_user row used to name the deleted user as the actor. It now names the admin or user who deleted the account, and resource_id is the deleted user.
  • SOC 2 and GDPR reports skip attempt rows, so critical operations are counted once (§ B108). Listings still show them.
  • Scheduled secret rotation records system as the actor.

Upgrade procedure

  1. Add the alert above before you upgrade.
  2. Upgrade. The migration runs on start: it adds the seq column and index, creates audit_chain_head, and seeds it from the newest existing row. Rows from before the upgrade keep the old hash formula and have no seq. The first new row is seq 1.
  3. If you use self_pki, make sure the database accepts writes before the first start, or the server will not come up.

Upgrade and operations

  • Stop every old replica first. Stop all pre-v4.12 replicas before the upgrade starts. A v4.11 writer that keeps running after the migration writes rows with no seq that chain from a chained row, and verification reports them as hash_mismatch. A downgrade followed by a re-upgrade does the same to the rows written while downgraded.
  • Backup and restore. backup create now reads every table in one transaction (a read-only REPEATABLE READ snapshot on Postgres), so audit_chain_head and audit_logs always agree in the file. backup restore recomputes the chain head from the restored audit_logs in the same transaction: the head becomes the seq and hash of the row with the highest seq, or seq 0 and the hash of the newest legacy row when no restored row has a seq (an empty hash when there are none). This covers pre-v4.12 backups, which have no audit_chain_head table. At startup the server also moves a head that lags behind the highest seq forward to that row; it never moves the head backwards. A backup taken by an older build while the server was writing can have a head that lags its rows, so on an older build take backups with the server quiesced.
  • Load and latency. Login, token refresh, token issue (OIDC callback), wrap and unwrap now write two chained rows each, an attempt row and a result row. Every chained write takes the lock on the single audit_chain_head row, so audit writes from all replicas run one at a time. Size the database for the extra writes and expect login latency to include two serialized audit inserts.
  • Sustained audit outage. Login and token refresh run behind the database retry circuit breaker, and an audit unavailable failure counts toward it. After retry.circuit_breaker.failure_threshold failures (default 5) the breaker opens, and requests on that breaker get 503 with Service temporarily unavailable, please retry instead of audit unavailable until retry.circuit_breaker.timeout (default 60 s) passes.
  • SQLite. SQLite runs in its default rollback-journal mode with the driver's default 5 second busy timeout. A long reader, such as a backup export or a large report, or a burst of writes, can make audit writes wait for the lock. If the wait runs out, a critical operation returns 503 audit unavailable and does not run, instead of running with its audit row silently dropped.
  • Open follow-ups are tracked in docs/known-bugs.md: § B106, § B107, § B109 and § B110 (see Known issues below).

What did not change

  • Existing audit rows are not rewritten.
  • Authorization and the audit query routes are unchanged.
  • /api/v1/health/* does not check the audit store.

Known issues

  • B106: queries filtered by action, outcome, user or resource can report gap or hash_mismatch on a valid chain.
  • B107: first-boot signing-key generation under the default jwt.key_source: os_store is not written to the audit chain.
  • B109: account-level authorization changes (user create and update, explicit-deny policies, provisioning grants) are still best-effort audit events, not fail-closed critical ones.
  • B110: an unfiltered audit query sorts the whole audit_logs table, because its seq ordering cannot use an index.
