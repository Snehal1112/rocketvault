# v4.11.0 — Certificate restore and renewal isolation

> The version number is provisional and may change before tagging.

This release closes a High-severity cross-vault path through certificate
backup and auto-renewal (`.claude/known-bugs.md` § B76, GitHub #65), makes
certificate issuance and renewal respect the signing key's lifecycle and the
`keys/sign` data action on every entry point (§ B77, GitHub #43), and fixes
two certificate status-code and input defects (§ B78, GitHub #67).

## Breaking changes

1. **Per-item backup blobs are sealed, and old blobs no longer restore.**
   `POST .../secrets/{id}/backup`, `.../keys/{id}/backup` and
   `.../certificates/{id}/backup` now return a blob that starts with `rvb2.`
   and is encrypted and authenticated with AES-256-GCM under a key derived
   from the master key with HKDF-SHA256. The blob still carries the item's
   full version history. `.../restore` refuses, with 400, any blob taken
   before this upgrade, any modified blob, and any blob sealed under a
   different master key. There is no switch to accept old blobs: an old blob
   and a hand-forged one look identical, and accepting either is the
   vulnerability this release closes. Like database backup files, blobs do
   not survive a master-key rotation (the values inside them were already
   master-key ciphertext, and rotation does not rewrite blobs you hold).
2. **Issuing or renewing a certificate needs `keys/sign`.** Besides
   `Microsoft.KeyVault/vaults/certificates/create`, the caller must hold
   `Microsoft.KeyVault/vaults/keys/sign/action` in the vault, and an explicit
   deny policy on `(keys, sign)` blocks it. This applies to
   `POST .../certificates` and `POST .../certificates/{id}/renew` (both route
   shapes), the MCP `create_certificate` and `renew_certificate` tools,
   `rocketvault certificate create` and `rocketvault certificate renew`. The
   roles that hold `keys/sign` are Key Vault Administrator, Key Vault Crypto
   Officer and Key Vault Crypto User. **Key Vault Certificates Officer alone
   is no longer enough.** Issuance still also requires the principal to own
   an enabled, usable key in the vault (§ B32), and Crypto User cannot create
   keys, so a principal that only holds Crypto User must already own a usable
   key. This mostly affects principals who own keys but no longer hold a key
   role. It is a deliberate divergence from Azure, where a certificate creates
   its own key.
3. **Auto-renewal re-checks the owner and stays in the vault.** The
   scheduler renews a certificate under its own vault's scope, skips a
   certificate with no vault, and renews only while the certificate's owner
   still holds `keys/sign` in that vault with no explicit deny. A refusal
   skips the row and writes a `cert_auto_renew` audit row with status
   `denied`; a fault in the check, or a scheduler built without the check,
   writes `failed`. A skipped row emits no expiry warning and is not counted
   in the scheduler's totals; the audit row, repeated at each scheduler run
   (daily by default, with no deduplication), is the only signal. A global
   admin who owns a certificate but holds no role granting `keys/sign` in its
   vault stops renewing: data-plane checks have no admin bypass. Granting the
   owner a role that holds `keys/sign` resumes renewal on the next run.
4. **Unusable keys cannot sign.** A revoked, disabled, expired or
   not-yet-active key can no longer issue or renew a certificate, as a leaf
   key or as a CA's own key, and auto-renewal of the certificates that use it
   stops too. A key whose rotation policy sets an expiry (`ExpiryDays`) and is
   not rotated in time lapses the same way. Certificates already issued are
   not revoked, disabled or deleted, and an exportable certificate still
   exports under its own rules; export does not look at the linked key's
   state.
5. **A CA is refused as a signer when its own key is not usable.** On create
   and on renew, a CA certificate cannot sign when its linked key is:
   - soft-deleted (recovering the key brings the CA back);
   - purged (permanent: certificates it signed can never renew until the CA is
     re-issued and they are re-issued under it);
   - expired, not yet active, revoked or disabled;
   - or when the CA's key link was cleared at restore (see item 6). A CA
     restored while its key sat in the recycle bin loses the link and stays
     stranded even after the key is recovered.

   Rotating a CA's key does not stop the CA from signing, because rotation
   updates the same key row.
6. **Cross-vault restores lose foreign links.** A certificate restored into a
   vault where its key or signing CA does not exist (or sits in the recycle
   bin) keeps its body, key copy and full version history, but loses those
   links, also on its archived versions. The loss is permanent for that
   row, so it will not renew there, and a restored CA cannot sign. The
   restore answers 200 and gives no signal that a link was dropped. A
   same-vault restore keeps every link, except when a transient read error
   makes the existence check fail, in which case the link is also cleared.
   Restore still never grants exportability.
7. **`validity_days` is capped at 36500** on create and renew (HTTP 400; the
   CLI reports the service error). A renewal that keeps the current period,
   including auto-renewal and the default period of `certificate renew`, is
   clamped to 36500 days, so certificates issued before the cap with a longer
   period keep renewing at the capped period.
8. **Status codes.** Certificate creation now answers 403 for a signing key or
   CA owned by someone else, or for an unusable signing key, and 404 for a
   key or CA that is not in the vault, instead of 500. The renew route
   answers 409 for an unusable key or a missing signing CA, instead of 500.
   A database fault while reading a signing key or CA answers 500 on both
   routes. That includes the renew route's key read, which used to answer 409
   in that case. Some refusals still answer 500, see "Known issues".

## Upgrade procedure

1. Before upgrading, note which items you rely on per-item backups for. After
   upgrading, take fresh backups of them. Restoring a blob taken before the
   upgrade fails with 400; keep old blobs only as a record. Full-database
   backups (`rocketvault backup`) are unaffected: they do not use the item
   blob seal.
2. List who holds roles in each vault:
   `rocketvault vault-access list --vault <name>`. Grant every principal that
   issues or renews certificates, and every owner of an auto-renewing
   certificate, a role that holds `keys/sign` if they have none yet, for
   example:
   `rocketvault vault-access grant <user> --role "Key Vault Crypto User" --vault <name>`
   (add `--principal-type service_account` for a service account). The
   principal must also own a usable key.
3. After the first scheduler run, query the audit log for the skipped rows
   (admin only):
   `rocketvault audit logs --action cert_auto_renew --from <date>`.
   Each row's details carry `status=denied` or `status=failed` and name the
   certificate that stopped renewing. The audit outcome column is never set
   for these rows (§ B98), so `--outcome` cannot select them; filter by
   action and read the status in the details.
4. A CA certificate that now refuses to sign because it records no signing
   key, or whose key is purged, cannot be repaired. Re-issue it with
   `rocketvault certificate create --is-ca --key-id <key-id> ...` over a key
   in the same vault, then re-issue the certificates it signed.

No schema migration runs.

## What did not change

- Existing certificates, keys, secrets and their versions are not modified by
  the upgrade.
- The owner comparison on the signing key and CA certificate (§ B32) is
  unchanged.
- Restore never grants exportability.
- Certificate and key export and the exporter roles are unchanged.
- Full-database backup and restore (`rocketvault backup`) are unchanged.
- No route was added, and no repository or database schema changed.

## Known issues

- **B99 (GitHub #66)**: deleted users and service accounts keep their
  `role_assignments`, so the `keys/sign` check keeps passing for an owner
  that no longer exists, and the scheduler keeps re-signing certificates that
  outlive their owner (on SQLite, where foreign keys are not enforced). Not
  fixed here.
- **GitHub #43** was written before the final design and its text does not
  match it: the shipped rule is that issuing needs a role grant that holds
  `keys/sign` and no explicit deny on `(keys, sign)`, and key rotation does
  not stop a CA from signing. The issue text was not edited; § B77 is
  authoritative.
- A refusal for lacking `keys/sign` is audited as `denied` over HTTP and as
  `failed` over the CLI, and the HTTP row does not say whether an explicit
  deny or a missing grant refused it.
- `POST .../certificates` checks `keys/sign` before it parses `ca_cert_id`, so
  a caller without `keys/sign` gets 403 where a malformed `ca_cert_id` would
  otherwise give 400.
- Still answering 500 (§ B78): "signing CA cannot sign certificates; reissue
  it with --is-ca" and CA inspection failures on both routes, and a CA that
  vanishes between two reads during create. A disabled or expired CA on
  renew reports the renewed certificate as disabled in its 409 message, and
  a disabled or expired CA certificate still issues on create (pre-existing).
- **B100 (GitHub #68)**: a vault member holding Certificates Officer and
  Crypto User can back up and restore another member's CA into the same
  vault and then issue leaves chaining to it, because restore keeps a key
  link that resolves in the vault without comparing owners, and the CA key
  gate does not either. Predates this release; not fixed here.
- Item-backup restore gives no signal when it drops a key or CA link (§ B76).
