# v4.8.0 — Identity and sessions hardening

> The version number is provisional and may change before tagging.

This release fixes four identity weaknesses from the 2026-09-30 audit of
`api/`: cross-user session revocation (#40), OIDC accounts that gained a
password without a working second factor (#55), sessions that survived
password, role and delete changes (#47), and TOTP code replay (#45). The
issues #40, #47, #45 and #55 close when this work is pushed. Full detail:
`.claude/known-bugs.md` (B72 to B75).

## Behavior changes

1. **Local login refuses accounts without a TOTP secret.** An account whose
   stored TOTP secret is empty can no longer log in with a password, even a
   correct one. The error reads exactly like a wrong code. Before this release
   any six digits worked for such an account, because an empty secret yields
   codes anyone can compute. In practice this affects only OIDC-provisioned
   users who set a local password (`rocketvault users update --new-password`,
   or `PUT /api/v1/users/{id}`). Admin-created users always had a secret.
2. **Setting a password on such an account enrolls TOTP.** The response of
   `PUT /api/v1/users/{id}` carries the new `otpauth://` URL in `totp_secret`,
   the same field `POST /api/v1/users` uses, and `rocketvault users update`
   prints it. It is shown once, the response is `Cache-Control: no-store`, and
   the secret is never logged or audited. Accounts that already have a secret
   keep it on every later password change.
3. **Password and role changes end every session of the user.** This
   includes the caller's own session when they change their own password, so
   the next CLI command or API call needs a new login. A username-only change
   keeps sessions, and so does re-submitting the roles the user already has.
4. **Deleting a user ends their sessions first**, and every authenticated
   user request now confirms that the token's user still exists. The
   revocation check already ran on every request; the new cost is the user
   read, `UserRepository.Read`, which is two queries (the `users` row by
   primary key and its `user_roles`). It also loads the user's
   `password_hash` and `totp_secret` into memory for the duration of the
   check. No cache was added.
5. **Each TOTP code works once.** A second login with the same code, or with
   a code from an earlier 30-second step, fails with `invalid TOTP code`. Two
   local logins by the same user inside one 30-second step need two different
   codes, so automation that reuses a code will break. This applies to the CLI
   and the HTTP login alike. If the server clock jumps forward, a login during
   the jump claims a far-future step, and every TOTP login of that user then
   fails until real time catches up with that step; see the known
   limitations below.
6. **A wrong-length TOTP code is now treated as an invalid code.** It is
   audited as `invalid TOTP code` instead of `TOTP validation error`. The HTTP
   response is unchanged: it was already, and still is, the generic `403`
   `authentication failed`. Only the CLI output changes: it now prints
   `invalid TOTP code` instead of an `authentication failed` wrapper around
   the library's length error.
7. **`DELETE /api/v1/users/sessions/{id}` is ownership-checked.** Admins can
   still revoke any session. Anyone else gets `404` for a session they do not
   own, the same answer as for a missing session. An admin revoking a missing
   session now also gets `404` instead of `500`.

## Schema

`users` gains `totp_last_step BIGINT NOT NULL DEFAULT 0`. It is added
automatically at startup (`createOptimizedSchema` for new databases,
`migrateSchema` for existing ones) on SQLite and Postgres; no manual step is
needed and existing rows start at 0.

## Upgrade procedure

1. Find accounts that the new login check will lock out (read-only):

   ```sql
   SELECT id, username, auth_provider FROM users
   WHERE (totp_secret IS NULL OR totp_secret = '') AND password_hash <> '';
   ```

2. Revoke the sessions of each account the query returns. Sessions and
   refresh tokens issued before this release to such accounts are not
   revoked by the upgrade, and a refresh token stays usable for up to 7 days.
   No API route or CLI command lets an admin list or revoke another user's
   sessions, so this step needs direct database access. Operators with that
   access run the following once, after taking a backup:

   ```sql
   UPDATE user_sessions
   SET revoked = TRUE, revoked_at = CURRENT_TIMESTAMP,
       revoked_reason = 'v4.8.0 upgrade'
   WHERE revoked = FALSE AND user_id IN (
     SELECT id FROM users
     WHERE (totp_secret IS NULL OR totp_secret = '') AND password_hash <> ''
   );
   ```

   It works on SQLite and Postgres. It is deliberately not a migration in
   `migrateSchema`: that function runs on every start, so the statement
   would revoke these users' sessions again at every restart until they
   enroll, including sessions from their OIDC logins.
3. Re-enroll each of those users. Setting a password on such an account
   generates a TOTP secret and prints it once, but only two kinds of caller
   can set it:
   - **An admin**, with `PUT /api/v1/users/{id}` or
     `rocketvault users update <user-id> --new-password <password>`. The
     admin receives the TOTP secret and must pass it to the user over a
     secure channel, so the admin learns it.
   - **Someone with shell access to the server host**, running
     `rocketvault users update` in local mode against the server's own
     configuration and database. A user can do this for their own account
     only if they have that access.

   A non-admin cannot do it remotely: `PUT /api/v1/users/{id}` requires the
   admin-only `users:update` permission, and `rocketvault users update` has
   no remote mode (only `users login` and `users logout` do). Their OIDC login
   keeps working the whole time.
4. Expect every user to log in again after they change their password or an
   admin changes their roles.

## Known limitations and operator warnings

- **TOTP lockout is accepted and has no reset path.** No command or endpoint
  resets a TOTP secret. A local account that has a password but no secret can
  only be recovered by editing the database; OIDC login still works for it.
  The same happens if the one-time enrollment URL is lost: when a transient
  error makes the retry wrapper re-run an update whose enrollment was already
  written, or when session revocation fails after it (see below), the
  response carries no URL and the account is locked out for password login.
  A failed read-back of the user after the update does not lose it: the
  `PUT /api/v1/users/{id}` response still carries the URL, with the other
  fields built from the request, and the read error is only logged.
- **A stolen session token of an OIDC user who holds the admin role can set
  a password** for that user and receive the enrollment URL over HTTP. For a
  non-admin OIDC user this needs shell access to the server host, because
  `PUT /api/v1/users/{id}` is admin-only and `rocketvault users update` has no
  remote mode. A fresh IdP login is not required before setting a password
  (step 5 of `.claude/research-oidc-user-mfa-enrollment.md`), and enrollment
  is not confirmed with a first code (step 6). Both are deferred.
- **An admin who sets an OIDC user's password learns that user's TOTP
  secret**, as with admin user creation.
- **Revocation can fail after the write succeeded.** The password or role
  change is not in one transaction with revocation. If revocation fails, the
  update returns an error but the change stays, old sessions stay alive
  (refresh tokens up to 7 days, the old role inside an access token up to 1
  hour), and a retry of the same update skips revocation for a role change
  because the roles now read as unchanged. A generated enrollment URL is lost
  in that case too. Revoke the user's sessions by hand if you see this error.
- **A forward jump of the server clock locks a user out of TOTP login for a
  while.** A login during the jump claims a step from the future. Codes from
  earlier steps are then refused as replays, so every TOTP login of that user
  fails until real time reaches the claimed step. OIDC login is unaffected.
  Keep the server clock synchronized.
- **Deleting a user revokes first.** If the delete then fails, the user is
  logged out but not deleted. This is fail-safe; repeat the delete.
- **A login that races a user delete** can leave one unrevoked session
  until the token expires; the user-exists check on every request still
  rejects it.
- **Refresh tokens are not rotated.**
- **Restoring a full database backup can revive old password hashes and
  sessions.** This was already the case and is not changed here.
