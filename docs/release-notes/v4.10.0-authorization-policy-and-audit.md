# v4.10.0 — Explicit-deny coverage, route authorization, and audit attribution

> The version number is provisional and may change before tagging.

This release fixes three findings from the 2026-09-30 static audit of `api/`:
GitHub #42 (`.claude/known-bugs.md` § B79), #50 (§ B80) and #49 (§ B81, which
supersedes § B58 and closes #18).

## Breaking changes

1. **Audit retention has a floor of 90 days.** `PATCH /api/v1/audit/config`
   and `rocketvault audit config --retention-days` refuse a value below 90. A
   value below 90 saved by an earlier version is read as 90, and
   `GET /api/v1/audit/config` reports 90 for it, not the stored number. The
   default stays 365.
2. **A deny on `create` no longer blocks five other operations.** See
   "Access policies" below. This loosens existing denies; audit them before
   deploying.

## Behavior changes for existing deployments

### Access policies: five operations now have their own names

`POST .../keys/{id}/encrypt`, `/decrypt`, `/wrap`, `/unwrap` and
`POST .../{secrets|keys|certificates}/{id}/backup` used to be evaluated
against the `create` operation. They now resolve to `encrypt`, `decrypt`,
`wrap`, `unwrap` and `backup`. `wrap` and `unwrap` are new operation values.
The CLI `keys wrap` and `keys unwrap` commands changed the same way, and
`keys import` now passes `import`, as the HTTP route does (B94), so both
entry points agree.

What this means for you:

1. A deny naming `encrypt`, `decrypt` or `backup` now takes effect over HTTP.
   Before, it was silently ignored there.
2. A deny on `(keys, create)` no longer blocks the five operations above, and
   a deny on `(secrets, create)` or `(certificates, create)` no longer blocks
   item backup. If you relied on that, add denies naming the operations.
3. A deny on `(keys, create)` no longer blocks `keys import` over the CLI;
   deny `import` instead.

Export is unchanged: it still resolves to `create`, so a deny on `create`
still blocks it. Find policies that may need a companion deny:

    GET /api/v1/access-policies

and look for rows with `"operation": "create"` and `"effect": "deny"`.

### Public endpoints are matched exactly

Only these paths skip authentication: `/api/v1/health`,
`/api/v1/health/ready`, `/api/v1/health/live`, `/api/v1/users/login`,
`/api/v1/users/refresh`, `/api/v1/oauth2/token`, `/api/v1/oidc/login`,
`/api/v1/oidc/callback`, `/api/v1/oidc/cli/exchange` and `/api/v1/config`.
Before, any path ending in `/login`, `/refresh`, `/register` or `/health`
skipped it, which made a vault with one of those names impossible to manage
over HTTP. Such vaults are manageable again with no action.

### Reserved vault names

New vaults may not be named `login`, `health`, `refresh` or `register`.
**Existing vaults with these names keep working** everywhere, including the
MCP server; nothing is renamed and no migration runs. After such a vault is
purged, its name cannot be reused.

### Startup refuses an unclassified route

The server now refuses to start if any registered route is neither a mapped
vault data-plane route nor on the non-data-plane allow-list in
`api/route_authorization.go`. This affects only builds that add routes; a
stock build always passes.

### Audit trail

- `revoke_role_assignment`, `delete_vault`, `recover_vault` and
  `purge_vault` rows now name the acting principal. Automatic vault purges by
  the soft-delete scheduler are recorded as `system`. Role-assignment
  rollback rows written by `AssignRole` name the caller too.
- Access-policy changes write `create_access_policy`,
  `update_access_policy` and `delete_access_policy` rows.
- Refused vault, role-assignment, access-policy and vault-webhook operations
  write a row with status `denied`, on HTTP and the CLI alike.
- Not yet audited: refused vault-provisioning-grant operations, refusals in
  the audit, users, jwks and oauth2 handlers, and failures after the service
  call for revoke and vault delete, recover and purge. See § B81.

## Known issues

Building the route allow-list found two problems that are not fixed here:

- **B96**: non-admin users cannot list or revoke their own sessions or read
  or update their own profile over HTTP. It fails closed.
- **B97**: `/health/database` returns raw driver error text to any
  authenticated caller.

Both are described in `.claude/known-bugs.md`.

## Upgrade procedure

1. Review explicit-deny policies on `create` as described above.
2. Deploy. No schema change runs.
3. Optionally, re-save audit retention if it was below 90:

       rocketvault audit config --retention-days 90
