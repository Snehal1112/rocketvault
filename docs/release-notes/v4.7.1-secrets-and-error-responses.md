# v4.7.1 — Secret lifecycle enforcement and safer error responses

The version number of this release is provisional until the release owner
assigns it.

This release closes three audit findings (GitHub #41, #44 and #48) and the
related bugs B55, B82, B83, B84 and B86; details are in `.claude/known-bugs.md`.
Plan: `docs/superpowers/plans/2026-09-30-secrets-and-error-responses.md`.

## The breaking change

Seven groups of API and CLI behaviour change. Clients and automation that
depended on the old behaviour need the updates in "Upgrade procedure" below.

### 1. 500 responses no longer carry the real error

Every 500 produced by `SetInternalError` (the shared API error path) now
carries a fixed `detailed_error`: `An internal error occurred. Quote the
request_id when contacting support.` The real error is written to the server
log under the response's `request_id`. The same applies to the JWKS rotate
endpoint, the OIDC handlers and `/health/ready`:

- `POST` JWKS rotate returns the same fixed `detailed_error`.
- `GET /health/ready` still answers 200 `{"status":"ready"}` or 503
  `{"status":"not ready"}`, but the body no longer has an `error` key.
- The OIDC login and callback endpoints answer with plain-text bodies:
  `authentication failed`, `internal error` or `invalid cli_redirect_uri`.
  Previously they echoed the underlying error text.

Clients that parsed `detailed_error` text must use `request_id` and the server
log instead.

Three kinds of 500 do not go through `SetInternalError` and keep their own
shape. `GET /health` answers a plain-text body (`Failed to collect health
metrics` or `Failed to encode response`). The JWKS document endpoint answers
`{"error":"failed to build JWK set"}` when it cannot build the key set. The
certificate and key export routes use their own R6 body,
`{"error":{"code":"internal_error","message":"internal server error"}}`. None
of these carries the underlying error text.

### 2. Duplicate names return 409, bad content types return 400

- Creating or restoring a secret, key or certificate whose name is already
  taken in the vault returns **409** with a fixed message instead of 500
  (B55 and B86, GitHub #51). This covers create, generate, key import and the
  three `.../restore` endpoints.
- A secret with an unsupported `content_type` returns **400** instead of 500.

### 3. `Cache-Control: no-store` on authenticated and JSON responses

JSON responses and authenticated responses now carry `Cache-Control:
no-store`, unless the handler chose its own value (the JWKS document keeps
`public, max-age=3600`). Responses written directly by middleware are not
covered: the 401, 403 and 429 answers produced by `http.Error` in
`internal/middleware`, the per-vault rate-limit 429, and the plain-text OIDC
error bodies carry no `Cache-Control` header.

### 4. Export and version reads respect the secret lifecycle

- Secret export omits disabled, expired and not-yet-active secrets, and
  soft-deleted ones, in every format (json, csv, and sealed). Re-enable a
  secret before exporting if it must be included.
- Reading a version's value (`GetVersion`, the latest version, the version
  list with values) of a disabled, expired or not-yet-active secret returns
  **403**. Version metadata listing stays allowed because it carries no
  plaintext.

### 5. `PUT /secrets/{id}` behaves like an update, not a read

- Enabling a disabled secret no longer returns 403, and a disabled secret's
  value and attributes can be edited (this matches Azure).
- Sending a value identical to the stored one no longer returns 400 "no
  changes provided". It is a real update and archives a new version. Only an
  empty body is rejected.
- When the update disables or expires the secret, the response is a minimal
  body (`id` and `enabled`). The minimal body can report `enabled: false` for a
  secret that is enabled but expired, when the request did not set `enabled`.
- `rocketvault secrets update` in remote mode sends the same `PUT`, so it now
  matches local mode on both points.

### 6. Import validates each item like create

Import runs the create validation on every item (name, value size, tag
count). Items that fail are not stored and are reported in the response:
`failed_count`, `errors` (`Invalid '<name>': ...`) and `skipped_count`. When
any item fails, the HTTP status is still 200 but `success` is `false`. The
remote CLI prints the per-item failures and exits non-zero.

A storage failure for one item is reported as a fixed class, never as the
database error: `'<name>': name already exists` or `'<name>': internal error`.
The real error is written to the server log.

An item with a missing name or value is appended to `errors` but counted in
`skipped_count`, not `failed_count`. Because `success` only reflects
`failed_count`, a response can have `success: true` while `errors` is not
empty. Check `errors` as well as `success`.

A file that cannot be parsed as the requested format (invalid JSON, or an
unreadable CSV header row) returns **400** instead of 500.

### 7. CSV export guards formula cells

CSV export (plain and sealed) prefixes any cell starting with `=`, `+`, `-`,
`@`, a tab or `'` with a single `'`, so spreadsheet software does not execute
a secret value as a formula. Import removes one leading `'` from a cell. Any
CSV not produced by this version (an export from an older version, a
hand-written file, or a file from another tool) whose cell genuinely begins
with `'` therefore loses that one apostrophe on import. JSON exports are
unchanged.

## Upgrade procedure

1. Update automation that keyed on `detailed_error` text. Use the HTTP status
   and `request_id`, and read the cause from the server log.
2. Update any readiness checker that read the `error` key of
   `/health/ready`; it now gets only `status`.
3. Re-run any export that must include disabled secrets after re-enabling
   them. Exports taken before this release may contain secrets that the new
   export would omit.
4. Treat 409 on create and restore as a name conflict to resolve (rename,
   purge or recover), not as a server fault to retry.
5. If a pipeline reads exported CSV files, expect a leading `'` on cells that
   start with a formula character. Re-importing through RocketVault removes
   it.
6. Update import callers to check `success`, `failed_count` and `errors`, not
   only the HTTP status. `errors` can be non-empty when `success` is true.
